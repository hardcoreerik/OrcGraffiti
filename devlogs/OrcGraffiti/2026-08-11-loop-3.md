# OrcGraffiti Devlog — Loop 3 (2026-08-11)

## Summary

Attempted AS-3 (`orcgraffiti paint --out`, 3MF write mode), found two real
bugs in the round-trip, fixed one, hit the second, and **reverted the
attempt** rather than commit a feature that silently writes unopenable
project files. This is the correct outcome of the risk this session's
previous devlog (loop-2) flagged — better to prove the risk real and back
out cleanly than to ship it unverified.

## What Was Done

### AS-3 write path — attempt

Extended `cmd_paint` in `src/orcgraffiti_cli/orcgraffiti.cpp`:

- `--out <path.3mf>`, `--force`, `--allow-in-place` flags; `--dry-run` and
  `--out` made mutually exclusive (exactly one required).
- `Model::read_from_file` called with real `DynamicPrintConfig`,
  `ConfigSubstitutionContext`, `PlateDataPtrs`, `vector<Preset*>` (not the
  `nullptr` defaults `info`/AS-2 use) so the loaded project's config/plates
  could round-trip through `store_bbs_3mf` unchanged.
- Reused `ImagePaintJob::finalize`'s apply pattern: `TriangleSelector`
  from the target mesh, `deserialize()` existing `mmu_segmentation_facets`
  first, overlay non-`kStateNone` plan states, `vol->mmu_segmentation_facets.set(selector)`.
- `store_bbs_3mf(StoreParams&)` with `SaveStrategy::Zip64`.

### Bug found #1: empty plate structure (fixed)

Testing `paint --out` against `unit_cube.stl` + `garth.jpg`: the write
succeeded (no crash, 2496-byte 3MF produced, `paint_color="0C"` correctly
present on the 2 painted triangles in `3D/3dmodel.model` — hand-verified by
unzipping). But `orcgraffiti info` on the written file failed:
`"The supplied file couldn't be read because it's empty."`

Cause: STL input has no BBS plate data, so the loaded `PlateDataPtrs` was
empty. Passed through unchanged to `store_bbs_3mf`, this wrote
`Metadata/model_settings.config` with no `<plate>` element — and
`load_bbs_3mf` needs one to populate `model.objects`.

Fix: when `plate_data.empty()`, synthesize a single default plate covering
every object/instance in the model, via `PlateData(0, obj_inst_set, false)`
where `obj_inst_set` holds `(object array-index, instance array-index)`
pairs (confirmed against `PartPlate.cpp:2755-2759` — `PartPlate::add_instance`
indexes `m_model->objects[obj_id]` directly, so these are array indices,
not `ObjectID`s).

### Bug found #2: obj_map lookup failure (NOT fixed)

After the fix, `model_settings.config` now had a correctly-shaped
`<plate>` element with `model_instance/object_id` matching the actual XML
resource id (`2`, matching `<build><item objectid="2">` in
`3D/3dmodel.model` — hand-verified again). Reload still failed, now with:

```
[warning] Slic3r::_BBS_3MF_Importer::_load_model_from_file:2363,
can not find object from plate's obj_map, id=2, skip this object
orcgraffiti: failed to load '...': The supplied file couldn't be read because it's empty.
```

The importer builds an internal `obj_map` while parsing `3D/3dmodel.model`
and, for a reason not yet isolated, doesn't find id=2 in it even though
`<object id="2">` is present in the same file. Did not have time this loop
to set a breakpoint in `bbs_3mf.cpp` and trace `obj_map`'s construction —
that's the concrete next step, not a re-guess.

One data point that may matter: the written `model_settings.config`
included `<metadata key="identify_id" value="14"/>` on the
`model_instance` — a value that came from *somewhere* (not something this
CLI code set explicitly), and it's unclear whether an `identify_id`
mismatch or omission is what breaks `obj_map` resolution.

### Decision: revert, don't ship

Getting a subtly-broken 3MF writer merged would violate this project's own
"no regressions in project compatibility" review focus and the
AGENTS.md-level bar this fork holds itself to. Ran `git checkout --
src/orcgraffiti_cli/orcgraffiti.cpp src/CMakeLists.txt` to cleanly revert
to the last commit (AS-2, already tested and pushed). Rebuilt and reran
`ctest -R "image_paint|orcgraffiti"` — **19/19 still green**, confirming
the revert left no residue.

## Known Gaps

- AS-3 (3MF write) still not implemented. Two concrete bugs documented in
  `AI_STATUS.md` for whoever picks this up — one fixed-but-insufficient,
  one unisolated.
- The recommended next approach needs either (a) interactive debugging of
  `_BBS_3MF_Importer::_load_model_from_file` with a real Orca-saved 3MF to
  diff against, which this headless loop can't do well, or (b) a product
  decision to narrow AS-3's v1 scope to the plain (non-BBS) `store_3mf`
  writer for non-3MF inputs — trading "reopens in this fork's GUI" for
  "opens in any 3MF-compliant tool." That's a real scope call, not
  something to silently decide inside a loop iteration — worth raising
  with the user directly.
