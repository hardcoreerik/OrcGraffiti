### Bug found and fixed: `LoadStrategy` for `.3mf` reads

Implementing the plain-3MF write, needed to verify round-trip by reloading
the written file via `orcgraffiti info`. That failed — but so did loading
**a real, pre-existing, known-good 3MF fixture**
(`tests/data/test_3mf/.../Büchse.3mf`) the exact same way:
`"The supplied file couldn't be read because it's empty."` This proved the
bug predates AS-3 entirely — `info`/`paint --dry-run` have never correctly
read any `.3mf` input, only ever tested against STL fixtures until now.

Root cause: `Model::read_from_file`'s default `LoadStrategy`
(`AddDefaultInstances` alone, value `1`) omits `LoadModel` (`4`) and
`LoadConfig` (`8`). Without those bits, the BBS 3MF importer silently
returns zero objects. `src/OrcaSlicer.cpp`'s own CLI ORs
`LoadModel | LoadConfig | AddDefaultInstances | LoadAuxiliary` in for any
`.3mf` load (line 1646) — our CLI's `Model::read_from_file(path)` calls
never did. Fixed with a shared `full_load_strategy()` helper used by both
`cmd_info` and `cmd_paint`. Verified against both the real fixture and the
CLI's own STL-sourced output — both now load correctly, with matching
fingerprints. Locked in with a new ctest entry,
`orcgraffiti_cli_info_3mf_fixture`, against a copy of the fixture renamed
to sidestep a non-ASCII-path issue in test tooling
(`tests/orcgraffiti_cli/fixtures/sample_project.3mf`).

### AS-3 v1: plain 3MF write path

With the read-side bug fixed, implemented `paint --out`:
- `--out <path.3mf>`, `--force`, `--allow-in-place`; `--dry-run`/`--out`
  mutually exclusive, exactly one required.
- Reused the `TriangleSelector` apply pattern from
  `ImagePaintJob::finalize` (deserialize existing facets, overlay non-none
  plan states, `set` back onto `mmu_segmentation_facets`).
- `Slic3r::store_3mf(path, &model, nullptr, /*fullpath_sources=*/false)` —
  much simpler than the BBS writer: no `PlateDataPtrs`/`project_presets`
  plumbing, no `release_PlateData_list` ownership concerns.

**Verified:** `paint --out` on `unit_cube.stl` + `garth.jpg` writes a file
whose mesh geometry and topology fingerprint match the original input
exactly (`0xfd4bcf4965f66135`/`0x4258fbbe9dd5a2a5`, bit-for-bit) when
reloaded through `orcgraffiti info`. No crash, no data loss on the
geometry side.

### Bug found #2: self-check reader mismatch, then a segfault (reverted)

`info` on the written file reported `has_mmu_paint: false` despite the
paint attribute being present (hand-verified: `triangle ...
slic3rpe:mmu_segmentation="0C"` in the raw zip's `3D/3dmodel.model`).
Cause: `store_3mf` writes the Prusa/Slic3r-family attribute name, but this
CLI's reader (`Model::read_from_file` → always `load_bbs_3mf`) only
recognizes the BBS-native `paint_color` attribute.

Found that the **real GUI** doesn't have this problem: `Plater.cpp:6897`
("Open Project") calls `Model::read_from_archive`, not
`Model::read_from_file` — `read_from_archive` runs
`PrusaFileParser::check_3mf_from_prusa` and routes Prusa/generic 3MF
through the plain `load_3mf` reader, which understands
`slic3rpe:mmu_segmentation`. Tried switching the CLI's own loader to
`read_from_archive` to match — **it segfaulted**, and critically, it
segfaulted on the **known-good fixture too**, both before and independent
of any of this session's paint changes. That ruled out "something wrong
with our written file" and pointed at a genuine `read_from_archive` usage
bug (not further diagnosed — out of scope to chase a second unrelated
crash this loop). Reverted immediately: `load_model_for_cli()` now always
uses `Model::read_from_file`, with the reader-mismatch limitation
documented in `--help` output and `AI_STATUS.md` instead of silently
hidden or half-fixed with a crash risk.

## Known Gaps

- AS-3's own self-check (`has_mmu_paint` via `info`) cannot currently
  detect paint on files it just wrote with `--out` — a manual GUI reopen
  is the only way to confirm the paint is actually visible. This is
  explicitly flagged in `--help` output, not silently swept under the rug.
- `Model::read_from_archive` segfaults in this CLI's usage, on any `.3mf`
  input, unrelated to paint — undiagnosed, not on today's critical path
  since `read_from_file` works fine for `info`/dry-run purposes.
- BBS-native `store_bbs_3mf` write path (preserving profile/plate data)
  remains unimplemented; investigation notes from loop 3 preserved in git
  history if ever revisited.
- `back`/`left`/`bottom` view presets still not individually locked by a
  golden test (carried over from loop 2).
