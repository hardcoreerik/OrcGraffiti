# OrcGraffiti Devlog — Loop 7 (2026-08-11)

## Summary

The user tested `gui_check_bbs_v2.3mf` (loop 6's "fixed" BBS writer) and
reported it **crashed OrcaSlicer 2.4.2 and FlashForge Studio on open**.
Found and fixed the root cause (a dangling 3MF package relationship
referencing a thumbnail file that was never written). Explicitly did not
send another test file without asking first, given the severity. Also
landed Phase 7's spherical projection while investigating.

## What Was Done

### The crash report

User: `"F:\Ai\OrcGraffiti\build\gui_check_bbs_v2.3mf" this stl cause a
crash when i opened it in OrcaSlicer 2.4.2 and flashforge studio`

This is qualitatively different from loop 6's "just a cube" failure — a
crash in *two independent, unrelated applications* on the same file
pointed at a structural validity problem in the archive itself, not a
paint-attribute recognition gap. Treated as a stop-everything issue:
immediately reverted the "AS-3 is fixed" framing, did not continue any
other work until this was at least understood.

### Root cause found

Inspected the crashing file with Python's `zipfile` module.
`_rels/.rels` referenced `/Metadata/plate_1.png` and
`/Metadata/plate_1_small.png` in three separate `Relationship` entries —
but `namelist()` showed no such files existed anywhere in the archive.
Traced this to `_BBS_3MF_Exporter::_add_relationships_file_to_archive`
(`bbs_3mf.cpp:6750`): when no thumbnail path is set in its internal
`PackingTemporaryData`, it falls back to hardcoded relationship targets
(`"Metadata/plate_1.png"`) *unconditionally* — it never checks whether a
file will actually exist at that path. Since `orcgraffiti` never supplied
`StoreParams::thumbnail_data`, the corresponding
`_add_thumbnail_file_to_archive` call never ran, so those files were
never written. The result: a structurally invalid OPC package with
dangling relationship references — very plausibly the kind of thing that
crashes readers which eagerly resolve relationships for UI purposes (e.g.
loading a cover thumbnail on file open), which would explain why two
independent applications both failed on it.

### Fix

Populate `StoreParams::thumbnail_data` with a minimal valid
`ThumbnailData` (16×16, `ThumbnailData::set()` defaults to white pixels)
before calling `store_bbs_3mf`. Confirmed
`_add_thumbnail_file_to_archive` uses miniz's built-in PNG encoder
(`tdefl_write_image_to_png_file_in_memory_ex`) with no wx/GUI dependency,
so this is safe to call from the headless CLI. With `generate_small_thumbnail=true`
(hardcoded for the main thumbnail call), this also produces the
`_small.png` companion the third relationship entry needs.

**Verified structurally**, not just via the CLI's own round-trip: unzipped
the newly-written file and confirmed `Metadata/plate_1.png` (87 bytes) and
`Metadata/plate_1_small.png` (143 bytes) both exist with valid PNG
signatures, and all four `_rels/.rels` entries now resolve to real files
in the archive. `has_mmu_paint` round-trip and the full 24-test ctest
suite still pass.

### Did not send another file without asking

Given the user already hit one crash from this feature, generating and
handing off a third test file without their explicit agreement would have
made them an unwitting repeat crash-test target. Updated `AI_STATUS.md`
with an explicit warning banner distinguishing "self-consistent per this
CLI's own checks" from "verified not to crash real software" — those are
different claims, and conflating them is exactly what went wrong in loop
6 (the CLI's own `has_mmu_paint: true` self-check passing was treated as
meaningfully positive signal, when it's actually a much weaker guarantee
than a human GUI check).

### Phase 7: spherical projection

While investigating/waiting on builds, implemented
`project_spherical`/`SphericalProjectionSettings` per `Roadmap.md` §11's
formula (`direction = normalize(p-center); longitude =
atan2(dot(direction,T), dot(direction,R)); latitude =
asin(dot(direction,A))`). Reused `CylinderFrame`/`make_cylinder_frame`
rather than introducing a duplicate orthonormal-frame type, since sphere
and cylinder projections need the same frame shape (origin + axis +
radial reference + tangent). `v` mapping mirrors the cylindrical
height/v convention (`v = 0.5 - latitude/PI`) without needing a separate
"height" setting, since a sphere's latitude range is fixed at
`[-pi/2, pi/2]` unlike a cylinder's variable height. 8 new tests, all
passed on first run.
