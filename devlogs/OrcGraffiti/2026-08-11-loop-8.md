# OrcGraffiti Devlog — Loop 8 (2026-08-11)

## Summary

The crash-fix from loop 7 was still broken — confirmed by the user with a
screenshot of FlashForge Studio hung indefinitely on load. This is the
second consecutive write-path fix that passed every self-check this CLI
could run and still failed a real-world test. Disabled `--out` entirely
rather than attempt a third blind fix.

## What Was Done

### The second failure

Sent `gui_check_bbs_v3_fixed.3mf` (the thumbnail-relationship fix from
loop 7, structurally verified: all zip relationship targets resolve to
real files) to the user after explicitly asking permission first. Result:
"no that didnt fix it. it stay stuck on this screen" with a screenshot
showing FlashForge Studio frozen on a "Loading file: gui_check_bbs_v3_fixed.3mf"
progress dialog, stuck partway through.

This is a different failure mode than loop 7's outright crash (a hang
instead), which is actually useful information — it suggests the earlier
crash and this hang may be different manifestations of related but
distinct problems in how a headlessly-constructed `Model` (with no real
`Plater`/`PartPlateList` behind it) interacts with `store_bbs_3mf`'s
assumptions about application state that's normally present.

### Decision: stop guessing, disable the feature

Two fix attempts in a row passed every check available to this CLI
(structural zip inspection, `has_mmu_paint` round-trip, fingerprint
matching) and both failed real-world testing. Continuing to iterate
blindly — find another plausible-looking gap, fix it, ask the user to test
a third time — would repeat exactly the failure pattern that already cost
two rounds of the user's time and trust, with no better odds of success
than the previous two attempts had.

Disabled `paint --out` explicitly rather than silently reverting to
"not implemented": the CLI now refuses with a clear, specific error
(`"--out is disabled: confirmed to crash/hang real slicer software..."`)
pointing at `AI_STATUS.md`'s bug history, so anyone (including a future
instance of this loop) hitting the disabled path understands why
immediately rather than wondering if it's a regression.

### Test and doc cleanup

- Replaced the write→reload round-trip ctest pair
  (`orcgraffiti_cli_paint_out_write` → `..._reload_has_paint`, added in
  loop 6) with a single `orcgraffiti_cli_paint_out_disabled` test that
  locks in the *disabled* state. This matters specifically because the
  previous tests would have kept passing if someone re-enabled `--out`
  without fixing the underlying issue — they only checked self-consistency,
  which is exactly what proved insufficient. The new test would fail loudly
  if `--out` silently started "working" again per its own checks alone.
- Rewrote `SKILL.md` and `--help` text to state plainly that `paint
  --dry-run` is the only supported paint mode, with a "Why `--out` is
  disabled" section for any agent (or human) who reads the skill file
  wondering why a documented-elsewhere feature doesn't work.
- Rewrote `AI_STATUS.md`'s AS-3 section as a 10-step chronology (bug found
  → fixed → self-verified → sent to user → user reports crash → repeat)
  so the pattern itself — not just the individual bugs — is visible to
  whoever picks this up next.
